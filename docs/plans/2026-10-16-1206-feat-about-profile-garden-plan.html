Key technical decisions

KTD1. Native Markdown content

Keep the public copy in Obsidian public/about.md and its snapshot in content/about.md. Use ordinary headings, lists, and links.

This follows R4 and the existing publisher. A single file keeps editing simple and avoids duplicating career data in component props.

KTD2. Profile styling and layout stay local

Use cssclasses: [profile-page] for article styling and body[data-slug="about"] for page layout. Reuse ConditionalRender in quartz.layout.ts for profile furniture.

Maintain a single title and a roughly 760-pixel reading column. Dates stack above descriptions on mobile. Reuse theme variables and the current public portrait.

This implements R5 and R6 without changing note rendering, emitters, or global theme configuration.

KTD3. Static native navigation

Add one ProfileNav component to the shared header. Its About and Garden anchors use existing Quartz path helpers and internal-link classes.

No new client script is needed. Root and nested routes must generate working hrefs, and active-page marking must remain accurate.

KTD4. Use existing metadata and publication

Use frontmatter title, description, and socialDescription for R7. Keep the existing content-index, sitemap, and social-image emitters.

Quartz emits about.html. Link to /about; verify host behavior rather than adding a second page for /about/.

During implementation, stage public copy in the isolated checkout and a disposable vault source. Apply final source edits on Pluto only under release authority.

High-Level Technical Design

The author selects public copy from Journey, then maintains the final page in the public Obsidian folder. The publisher copies that source into Pawhouse. Quartz builds the snapshot; the existing Pages workflow publishes it.

Source review is private scratch work. Do not commit raw Journey extracts or a private source map into Pawhouse, including its docs.
